# Cross-Stack Audit — Wave 14 (2026-04-21)

Consolidated findings across TinkerBox (Dragon server) + TinkerTab (ESP32-P4
firmware), generated by 5 parallel audit agents immediately after Wave 13
closed. Wave 13 items (C1–C6 + H1–H10) are **not repeated here** — this doc
only lists new or residual issues.

Each item has a stable ID for wave-closure tracking.

- `[CRITICAL]` — production-affecting, crash or silent-wrong-answer today
- `[HIGH]` — latent bug that bites under load or attack
- `[MEDIUM]` — correctness / hygiene that will bite a future refactor
- `[LOW]` — paperwork, style, observability polish

Repo tags: `TB` = TinkerBox (Python), `TT` = TinkerTab (firmware), `OPS` =
infra / CI / deploy, `DOC` = documentation drift.

## CRITICAL

### W14-C01 `[TT]` `touch_ws_release` passes a string literal to a raw-masked WS send

- **File:line:** `main/touch_ws.c:294-297`
- **Issue:** `esp_transport_ws_send_raw(... "{\"t\":[]}" ...)`. ESP-IDF masks outgoing frames *in place*; the literal lives in `.rodata` (XIP-PSRAM on P4) so every touch release corrupts read-only memory.
- **Fix:** Copy to a stack buffer first, matching the pong pattern at lines 142–173 of the same file. One-line change.

### W14-C02 `[TT]` OTA check NULL-derefs second `esp_http_client_init`

- **File:line:** `main/ota.c:90-91`
- **Issue:** Under heap pressure the second `esp_http_client_init` returns NULL; the next line calls `esp_http_client_open(client, 0)` unconditionally. WDT reboot on a user-reachable path (Settings → Check Update).
- **Fix:** `if (!client) { free(body); return ESP_ERR_NO_MEM; }` between lines 90 and 91.

### W14-C03 `[TT]` Transcription queue NULL-derefs `esp_http_client_init`

- **File:line:** `main/ui_notes.c:1066-1067`
- **Issue:** Same class as W14-C02. On fragmented SRAM, `esp_http_client_init` returns NULL and `esp_http_client_set_header` on NULL crashes the transcribe queue task. Transcription silently dies until reboot.
- **Fix:** Guard before `set_header`; mark the note `NOTE_STATE_FAILED` on failure.

### W14-C04 `[TB]` WS `/ws/voice` register frame performs zero identity validation

- **File:line:** `dragon_voice/server.py:1556-1619` + `:157` (public allowlist)
- **Issue:** `register` frame only requires a non-empty `device_id` string — no bearer, no HMAC, no hardware_id proof. Exposed on ngrok. The P13 session-eviction path lets attackers kick real Tab5s. Full impersonation: replay conversation, drive LLM spend against OpenRouter/TinkerClaw, mutate memory + notes DBs.
- **Fix:** Require `Authorization: Bearer <DRAGON_WS_TOKEN>` on the WS upgrade request, OR add a signed `hwauth` field in the register frame and `hmac.compare_digest` it before `_upsert_device`.

### W14-C05 `[TB]` `NotesDB` runs synchronous `sqlite3` on the asyncio event loop

- **File:line:** `dragon_voice/notes/db.py:49` + all CRUD methods
- **Issue:** Called from aiohttp handlers in `notes/api.py` — every Notes POST/GET blocks the loop. A notes-search with a large corpus stalls WS pings long enough to trip the 45 s timeout in `server.py:1005`.
- **Fix:** Port to `aiosqlite` like `dragon_voice/db.py`, OR wrap every call in `await asyncio.to_thread(...)` under a lock. Sec audit also flagged this independently.

### W14-C06 `[TB]` Fire-and-forget `asyncio.create_task` leaks — 3 sites

- **File:line:** `notes/service.py:92`, `notes/service.py:109`, `server.py:1505`
- **Issue:** Tasks not stored, not cancelled on shutdown, exceptions silently swallowed. Ruff `RUF006` flags all three. Orphan embedding runs survive service shutdown → "Task was destroyed but it is pending" noise; orphan `speak_system` tasks wedge Piper mid-synthesis past WS close.
- **Fix:** `self._bg_tasks: set[asyncio.Task]` + `task.add_done_callback(self._bg_tasks.discard)`; await/cancel on shutdown (same pattern wave 13 H3 used for media_cleanup).

## HIGH

### W14-H01 `[TB]` `GET /api/config` leaks `api_token` + `tinkerclaw_token` cleartext

- **File:line:** `dragon_voice/config.py:326-331` (`config_to_dict`), `server.py:831-835`
- **Issue:** `redact_secrets=True` only matches `api_key`-suffixed fields. `server.api_token` and `llm.tinkerclaw_token` pass through verbatim to any authenticated caller. Compromise-escalation: bearer-holder pivots to gateway token and self-verifies the REST bearer.
- **Fix:** Broaden redaction predicate to `("api_key", "token", "password", "secret")`; add regression test that the env-set tokens never echo.

### W14-H02 `[TB]` Dashboard SPA injects server-controlled strings into `innerHTML` — stored XSS via device register

- **File:line:** `dashboard.py:1285-1291`, `:1307-1316`, `:1776-1833`
- **Issue:** `d.name`, `d.hardware_id`, `d.platform`, `d.firmware_ver`, `s.id`, `s.type` interpolated into template literals with no `escHtml`. Chains with W14-C04: attacker registers `hardware_id="<img src=x onerror=fetch('/api/v1/memory')…>"`, fires whenever an operator opens Devices/Overview. Dashboard fetch context carries `DRAGON_API_TOKEN`.
- **Fix:** Route every server-controlled string through the existing `escHtml` helper (line 1564). Move `${d.id}` out of inline `onclick` into `dataset` attributes.

### W14-H03 `[TB]` Rich-media `proxy_image` is SSRF-reachable from prompt-injection

- **File:line:** `dragon_voice/media/pipeline.py:134-150` + `:97-105`
- **Issue:** LLM output is scanned for `https?://…\.(jpg|png|gif|webp)` URLs and fetched with no allowlist, no private-IP filter, no redirect cap; size checked AFTER full body read; session-level timeout is unset. Reach: web_search → prompt-injection → LLM emits URL → Dragon fetches `http://169.254.169.254/…` or `http://127.0.0.1:11434/…`. Responses stored in `/home/radxa/media/` and served via the public `/api/media/` allowlist — Dragon becomes an open SSRF + exfil proxy.
- **Fix:** Resolve host; reject loopback/link-local/RFC1918/multicast. Cap redirects ≤2. Stream-read with running byte counter. Set session `ClientTimeout(total=20, sock_connect=5)`. See also W14-H04.

### W14-H04 `[TB]` `/api/media/*` public prefix — 48-bit media_id is "auth by obscurity"

- **File:line:** `dragon_voice/server.py:159` (allowlist) + `api/media_routes.py:39-62`
- **Issue:** `media_id = uuid.uuid4().hex[:12]` = 48 bits. Returned plaintext in every `media` / `user_media` WS event to any caller. Combined with W14-C04, any attacker who registers scrapes the ID stream.
- **Fix:** Require the bearer on `/api/media/{id}`, OR signed short-lived URLs (HMAC over `media_id + expiry + session_id`). At minimum widen to `uuid4().hex` (128 bits) and scope lookups to the requesting session.

### W14-H05 `[TB]` CORS `Access-Control-Allow-Origin: *` hard-coded in 3 sites, bypassing the allowlist middleware

- **File:line:** `api/messages.py:63`, `api/completions.py:47`, `dashboard.py:128` + `:141`
- **Issue:** `_cors_middleware` enforces a 4-origin allowlist, but the two SSE endpoints and the dashboard proxy stamp `"*"` on their own responses. SSE endpoints are the two highest-LLM-spend routes.
- **Fix:** Delete the hardcoded headers; let the middleware decide. If SSE specifically needs CORS, mirror `request.headers["Origin"]` against `_CORS_ALLOWED_ORIGINS`.

### W14-H06 `[TT]` Suspended-task leak family — 8 KB per user action, unbounded

- **Files:** `main/ui_voice.c:1569-1606+` (mode_switch_*), `main/ui_wifi.c:168/201/276-383`, `main/ui_home.c:1419-1462` (media_fetch), `main/chat_session_drawer.c:325-491` (drawer_fetch)
- **Issue:** Every spawn uses `xTaskCreatePinnedToCore(... NULL)` and the task ends with `vTaskSuspend(NULL)` (wave 13 C4 pattern). Each spawn leaks one 8 KB-stack TCB forever. Mic-tap x40 = 320 KB permanent PSRAM loss; 200+ drawer opens = ~1–2 MB. PSRAM-frag watchdog eventually reboots.
- **Fix:** Unified refactor: single long-lived worker task per use case fed by a FreeRTOS queue. Cheaper alternative: static `TaskHandle_t s_*_task` + a guard bool refusing re-spawn while in flight. Same cleanup covers all four sites.

### W14-H07 `[TT]` Undersized task stacks doing FATFS + I2S + LVGL work

- **Files:** `main/ui_notes.c:1438` (`sd_record_task`, 4 KB) · `main/ui_audio.c:45` (`PLAYBACK_STACK_SIZE 4 KB`) · `main/heap_watchdog.c:282` (3 KB)
- **Issue:** FATFS sector buffers (~2–4 KB) + libc FILE state + periodic LVGL calls exceed 4 KB. Long offline recording or WAV playback traps `stack_chk_fail`. The heap-watchdog task itself can stack-overflow during the fragmentation storm it's meant to report.
- **Fix:** Bump `sd_record_task` and `playback_task_fn` to 8 KB, `heap_watchdog_task` to 4 KB. One-line changes. PSRAM cost is trivial.

### W14-H08 `[TB]` Blocking file I/O in async request handlers (6 sites)

- **Files:** `api/system.py:37`, `api/system.py:55`, `api/synthesize.py:162`, `api/synthesize.py:213`, `api/media_routes.py:52`, `tools/system_tool.py:18`
- **Issue:** Plain `open(...).read()` in `async def` handlers. `synthesize.py:213` streams 4 MB firmware in 8 KB sync chunks. `media_routes.py:52` reads up to 8 MB camera JPEG on the loop thread. Ruff `ASYNC230` flags all six. Wave 13 H2 claimed `media_routes.py` was fixed; only `_handle_user_media` in `server.py` was actually migrated.
- **Fix:** `await asyncio.to_thread(path.read_bytes)` for small files; `web.FileResponse(path)` (sendfile) for firmware. Regression-test under voice load that OTA downloads don't stutter WS audio.

### W14-H09 `[TB]` MediaPipeline + MediaStore block the event loop on hourly cleanup

- **File:line:** `dragon_voice/media/pipeline.py:159` (lazy session, no timeout, never closed), `media/store.py:59/94-123` (sync `Path.write_bytes`, `iterdir`, `stat`, `unlink`)
- **Issue:** `_media_cleanup_loop` scans up to 500 MB of `/home/radxa/media/` synchronously on the loop once per hour — blocks WS pings long enough to trip the 45 s Tab5 keepalive during a voice turn. Separately, `MediaPipeline`'s lazy `aiohttp.ClientSession` is never closed on shutdown (wave 13 H3 fixed the *task*, not the session).
- **Fix:** Wrap `cleanup`/`store` in `await asyncio.to_thread(...)`. Add `await self._media_pipeline.close()` to `VoiceServer._on_shutdown`. Give the ClientSession a default `ClientTimeout(total=15)` at creation.

### W14-H10 `[TB]` Single shared aiosqlite connection serializes every DB op

- **File:line:** `dragon_voice/db.py:35/194` (single `self._db`), `server.py:418` (`_periodic_purge`), `memory.py:335` (ingest loop)
- **Issue:** All queries funnel through one aiosqlite connection. `purge_old_messages` runs two multi-second `DELETE ... WHERE NOT IN (SELECT ...)` on the same connection — starves the conversation engine for seconds during a Tab5 turn. `ingest_document` loops `execute` per chunk instead of `executemany`.
- **Fix:** Short term: batch the purge with `LIMIT N` + `await asyncio.sleep(0)` between batches. Medium term: a second short-lived connection for purge; `executemany` for document ingest. Long term: consider a connection pool.

### W14-H11 `[TB]` `MemoryService` creates a fresh `aiohttp.ClientSession` per embedding call

- **File:line:** `dragon_voice/memory.py:144`
- **Issue:** `_get_embedding` opens `async with ClientSession() as session:` every call — fires before every LLM turn and loops per-chunk on doc ingest. 200-chunk document = 200 socket open/close cycles. Same pattern wave 13 H4 closed on the dashboard, still live here.
- **Fix:** Lazy-init `self._http_session` in `MemoryService.initialize()`; close in new `shutdown()` wired into `VoiceServer._on_shutdown`.

### W14-H12 `[TB]` `MediaPipeline` session never closed on shutdown

- *(same underlying finding as W14-H09 session half — tracked separately for close-list accounting)*
- **Fix:** `await self._media_pipeline.close()` in `_on_shutdown`.

### W14-H13 `[TB]` Residual broad `except Exception` sites hiding real bugs (Wave 13 closed 3; ~17 remain)

- **Files:** `server.py:718/742/782/806/1060/1064/1071/1543/1705/1907/2131/2134/2228`; `media/pipeline.py:83/93/104/196`; `memory.py:194/218/243`; `tts/kokoro_tts.py:61`, `tts/piper_tts.py:175`, `tts/edge_tts_backend.py:54`
- **Issue:** Receipt-emit paths on `server.py:2131/2134` silently disable cost tracking on a `price_for_model` bug. Embedding failures in `memory.py` are silently downgraded to debug — Ollama outage silently degrades semantic search with no alert. `media/pipeline.py` renderer wraps swallow Pillow crashes. Ruff `BLE001` flags ~100 total across tree.

### W14-H14 `[OPS]` Six systemd units unhardened

- **Source:** `ssh radxa@192.168.1.91 'systemctl cat tinkerclaw-*'`

## MEDIUM

### W14-M01 `[TT]` Torn reads in `voice_get_*()` — readers skip the mutex that writers take

- **File:line:** `main/voice.c:2557-2570` (readers), writers at `:685-695`, `:641-658`
- **Issue:** `voice_get_last_transcript`, `voice_get_stt_text`, `voice_get_llm_text` return raw static buffers without `s_state_mutex`. Writers hold it. LVGL chat poll copies a mid-`strcat` string missing its NUL → OOB read in LVGL label renderer. Wave 13 H1 fixed the enum; this is the string half.
- **Fix:** Getters copy-under-mutex into a caller buffer (new signature), OR chat poll takes the mutex during copy.

### W14-M02 `[TT]` Playback-buffer overflow log emitted inside `s_play_mutex` — cascade risk

- **File:line:** `main/voice.c:379-402`
- **Issue:** `playback_buf_write` holds `s_play_mutex` across `ESP_LOGW` on the overflow path. Log format is ~100–500 µs; the mutex gates the drain task. One overflow → log serialized with drain → drain misses I2S deadline → more overflow → storm.
- **Fix:** Capture counters under the mutex; release; log outside.

### W14-M03 `[TT]` `s_ws` and `dragon_link.s_state` are non-volatile and read outside mutex

- **Files:** `main/voice.c:162` (`s_ws` decl, 9 reads cross-core), `main/dragon_link.c:30` (`s_state` decl, cross-core read at `:344-347`)
- **Issue:** No `volatile`, no consistent lock. Writer on Core 1 (connect/disconnect), readers on Core 0 (LVGL). No torn-read on pointer on ARM, but compiler may cache the load across a disconnect → use-after-free inside esp_websocket_client on a Dragon-restart race. Similar on dragon_link: stale "discovering" pill after reconnect.
- **Fix:** `volatile` qualifier on both, OR extend `s_state_mutex` / `dragon_link` mutex coverage.

### W14-M04 `[TT]` Unchecked `fread` while "repairing" WAV headers writes stack garbage on SD read failure

- **File:line:** `main/ui_notes.c:1037/1043/1045`
- **Issue:** `fread(&hdr_data_size, 4, 1, f)` return ignored. On short read, stack variable holds garbage; subsequent `fwrite` commits garbage into RIFF/data size fields → silent corruption of user recordings on a failing SD card.
- **Fix:** Check each `fread`/`fwrite` return; abort repair on failure.

### W14-M05 `[TB]` `serve_media` still blocks the event loop (wave 13 H2 partial)

### W14-M06 `[TB]` No CSP / `X-Content-Type-Options` / `X-Frame-Options` / `Referrer-Policy` headers

- **Files:** `dashboard.py:189` (DASHBOARD_HTML), `server.py:695` (`_handle_status`), every response

Dashboard CSP template: `default-src 'self'; style-src 'self' 'unsafe-inline' fonts.googleapis.com; font-src fonts.gstatic.com; connect-src 'self'`.

# Local-mode model gauntlet (2026-04-24)

Driven from the TinkerTab side as part of the TinkerClaw + Local mode stress
audit.  Goal: re-benchmark every sub-4B Ollama model installed on Dragon (plus
two HF-pulled tool-calling candidates) against the same 5 tool-forcing
prompts, crossed against the memory DB to distinguish real tool fires from
verbal acknowledgements.

## Methodology

**Driver:** `/tmp/gauntlet.sh` (bash helper kept in audit-artifacts drive).
For each model: `sed` swap of `dragon_voice/config.yaml` `ollama_model`,
`systemctl restart tinkerclaw-voice`, then 5 prompts via Tab5's `/chat` HTTP
endpoint (not on-screen keyboard — the tool-call path is Dragon-side so input
method doesn't change the outcome, but this way the gauntlet ran across 11
models in ~45 min wall-clock).

**Prompts (all 5 independent, clear-started between):**
1. G1 — `What time is it right now` (expects `datetime` tool)
2. G2 — `What is four hundred fifty six times seven hundred eighty nine` (expects `calculator`; actual answer **359,784** — deliberately not a memorized number)
3. G3 — `Remember my favorite color is magenta` (expects `store_fact`; verified via `GET /api/v1/memory`)
4. G4 — `Convert fifty celsius to fahrenheit` (expects `unit_converter`; correct = 122 °F)
5. G5 — `Set a timer for ten seconds` (expects `timesense` tool → `widget_live` on Tab5 home)

**Scoring:**
- Tool fires = `tools=N` log lines with N ≥ 1 from `dragon_voice.conversation` during the window.
- Mem-DB writes = new rows in `facts` whose `content` mentions "magenta" during the window.
- Median latency = middle value of the 5 per-prompt wall-clocks (capped at 120 s).

## Three failure classes observed

1. **Too small to tool-call** (qwen3:0.6b, qwen3:1.7b) — malformed XML or give up silently.
2. **Too slow for keepalive** (every 4B-class model) — Tab5's ~30 s WS PONG window is a hard wall; P13 guard evicts the reconnecting Tab5 and drops the in-flight reply.
3. **Fluent hallucinators** (llama3.2:3b, hermes3:3b, phi4-mini) — confident chatty answers that never invoke a tool. **Most dangerous class** — silent-fail models are obviously broken; hallucinators feel reliable until you verify the numbers.

## Resolution

- Default swapped to **ministral-3:3b** (2026-04-24, W15-OPS-2 in `WAVE-15-PROGRESS.md`).
- CLAUDE.md "Local LLM Benchmarks" section rewritten with all 11 rows.
- LEARNINGS.md entry **#78** documents the keepalive-ceiling insight and the prevention rules (non-memorized test inputs, cross-check against memory DB, screen for the three failure classes).
- Known gap: G5 `timesense` / `widget_live` emission works on zero of the tested models.  That's a system-prompt / tool-format issue upstream of model choice — filed as follow-up, not a local-model problem.
- Known gap: G1 `datetime` works on ministral-3 sometimes, fails silently other times. Current 3/5 fire-rate ceiling is upstream of this recommendation; further improvement requires either (a) switching tool format out of XML for local models, or (b) trying purpose-built function-calling models (see "Not yet tested" below).

### Parser patch (committed on `feat/tool-call-standard-parser`)

1. Open-tag regex widened from `<tool>` to `[<\[]tool[>\]]` — accepts
   `<tool>`, `[tool>`, `<tool]`, and `[tool]`.  Closing `</tool>` is
   always intact so no ambiguity.
2. New anchor pass for the standard dialect
   `<tool_call>{"name": "...", "arguments": {...}}</tool_call>`.
   Whitespace / newlines between the tag and the JSON tolerated.
3. 11 unit tests cover both dialects + all four bracket quirks + mixed
   chains + malformed input rejection.

### Why xLAM isn't the new default despite firing more tools

xLAM is a **tool-caller with no conversational head** — after the tool
executes, the model has nothing to say back to the user.  `last_llm_text`
is empty on 5/5 gauntlet turns, which means Tab5's chat bubble is blank
even when the tool correctly fired and stored a fact.  In voice UX,
"user sees nothing in their chat bubble" is a worse experience than
"user sees a wordy ack for a tool that sometimes didn't fire."

ministral-3:3b fires fewer tools but always produces a natural
conversational wrap (`"Got it, magenta's your jam! Ready to help with
anything else?"`).  Keeping ministral-3 as the default.

xLAM becomes valuable in a **dual-model pipeline**: xLAM picks the tool,
a second small model (ministral / cloud) wraps the result in natural
language.  This PR unblocks that architecture without locking it in.

## What's actually blocking Local-mode from being great

After three rounds, the pattern is clear and it's NOT "we haven't found the right model":

1. **Dragon's ~30 s WS keepalive** kills every 4B-class model regardless of accuracy.  Fix is either a keepalive bump on Tab5 or P13-eviction grace-period on Dragon.
2. **Small models that are trained for function-calling** don't also generate a conversational wrap.  Fix is a dual-model pipeline (tool-caller + responder) or a conversation-engine change that generates natural-language wrap from tool results.
3. **Tool-call dialect fragmentation** was partially addressed by PR #74 (legacy + standard dialects).  Third-dialect models (`<tool_X>...`) remain unsupported on purpose — supporting them requires either name-collision disambiguation or a Jinja template per model that coerces the output.

Model choice alone will never get tool-fire reliability above ~80 % on
